# Архитектурные решения

## ADR-001: Выбор PDF-парсера для годовых отчетов

### Контекст

RAG-корпус состоит из годовых отчетов компаний, в которых есть как обычный текст, так и сложные таблицы.

На одних и тех же страницах годового отчета ЛУКОЙЛ за 2024 год были протестированы три подхода к PDF parsing:

- pypdf
- pdfplumber
- PyMuPDF

Для сравнения использовались:

- страница 28 — обычный связный текст;
- страница 30 — таблица климатических рисков.

### Наблюдения

**pypdf**
- В целом корректно извлек обычный текст.
- Иногда добавлял ошибочные пробелы внутри слов.
- Содержимое таблицы извлекалось как обычный текст.
- Структура строк и колонок таблицы не сохранялась.

**pdfplumber**
- Извлек обычный текст чище.
- Лучше сохранил порядок чтения на сложной странице.
- `extract_table()` смог восстановить строки, колонки и связь между ячейками таблицы.

**PyMuPDF**
- В целом корректно извлек обычный текст.
- На сложной табличной странице сильнее дробил текст на отдельные строки.
- Обычный `get_text("text")` не сохранял явную структуру таблицы.

### Решение

Использовать `pdfplumber` как основной PDF-парсер в первой версии RAG-системы.

Использовать:

- `extract_text()` — для обычного текста;
- `extract_table()` — для страниц, где необходимо сохранить структуру таблицы.

`pypdf` оставить для простых технических операций с PDF, например подсчета количества страниц.

Решение пока считается предварительным, пока `pdfplumber` не будет проверен на отчетах всех трех компаний.

### Последствия

Преимущества:

- более чистое извлечение текста;
- лучшее сохранение порядка чтения;
- возможность извлекать таблицы как строки и колонки;
- одна библиотека подходит и для текста, и для таблиц.

Риски и ограничения:

- таблицы, которые продолжаются на нескольких страницах, требуют дополнительной обработки;
- качество parsing может отличаться для разных компаний и разных шаблонов PDF;
- сканированные или image-based страницы могут потребовать другого подхода, например OCR.

## ADR-002: Выбор базового retrieval и результаты Hybrid

### Контекст

Для текстового RAG были протестированы три подхода:

1. Dense retrieval на multilingual-e5-small.
2. BM25.
3. Hybrid retrieval: Dense + BM25 через Reciprocal Rank Fusion (RRF).

Оценка проводилась на одном golden dataset из 10 вопросов
с одинаковыми:

- chunks: size=1200, overlap=200;
- metadata filters: company + year;
- top_k=5;
- метриками Recall@1, Recall@3, Recall@5 и MRR.

### Результаты

| Retriever | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---:|---:|---:|---:|
| Dense | 0.650 | 0.950 | 1.000 | 0.850 |
| BM25 | 0.550 | 0.600 | 0.600 | 0.650 |
| Hybrid RRF 1:1 | 0.600 | 0.700 | 0.800 | 0.750 |
| Hybrid RRF 2:1 | 0.600 | 0.800 | 0.900 | 0.770 |

### Наблюдения

Dense retrieval показал лучший общий результат.

BM25 иногда улучшает позицию релевантного документа при наличии
точных лексических совпадений, но значительно хуже работает
на семантических запросах.

Обычный RRF дает Dense и BM25 одинаковый голос, из-за чего
нерелевантный документ, найденный обоими retriever'ами,
может обогнать релевантный документ, найденный только Dense.

Weighted RRF 2:1 улучшил Hybrid относительно RRF 1:1,
но всё равно не превзошел чистый Dense.

### Решение

На текущем этапе Dense retrieval используется как основной retriever.

BM25 и Hybrid сохраняются как экспериментальные компоненты,
но не используются как основной retrieval pipeline.

Следующий эксперимент — reranking Dense-кандидатов с помощью
Cross-Encoder.

### Ограничения

Golden dataset пока содержит только 10 вопросов.
Не следует дополнительно тюнинговать веса RRF на этом наборе,
чтобы не переобучаться на маленькой выборке.

## ADR-003: Dense retrieval + Cross-Encoder reranking

### Эксперименты

Сравнивались:

1. Dense E5 → Top-5
2. Dense E5 → Top-20 → GTE reranker → Top-5
3. Dense E5 → Top-5 → GTE reranker → те же Top-5

### Результаты на 20 golden-вопросах

| Pipeline | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---:|---:|---:|---:|
| Dense | 0.717 | 0.958 | 1.000 | 0.900 |
| Dense Top-20 + GTE | 0.742 | 0.950 | 0.975 | 0.917 |
| Dense Top-5 + GTE | 0.792 | 0.958 | 1.000 | 0.950 |

### Решение

Основной retrieval pipeline:

metadata prefilter
→ multilingual-e5-small Dense Top-5
→ gte-multilingual-reranker-base
→ reranked Top-5.

Reranker используется только для изменения порядка уже найденных
Dense Top-5 кандидатов.

Это сохраняет Recall@5 = 1.0 и улучшает Recall@1 и MRR.

Перед финальной оценкой проекта golden dataset должен быть расширен.

## ADR-004: Разделение текстового RAG и структурированных финансовых фактов

### Контекст

В проекте есть два принципиально разных типа пользовательских запросов.

Первый тип — качественные вопросы по содержанию документов, например:

- какие риски описывает компания;
- какие стратегические приоритеты указаны в отчете;
- какие факторы влияли на деятельность компании.

Для таких вопросов нужен поиск релевантных фрагментов текста и генерация ответа
с опорой на найденный контекст.

Второй тип — запросы точных финансовых значений, например:

- выручка за конкретный год;
- EBITDA;
- чистый долг;
- операционный денежный поток.

Использовать vector retrieval как источник истины для таких значений рискованно:
retriever ищет семантически похожий текст, но не гарантирует извлечение именно
нужного числа, периода, единицы измерения и версии показателя.

### Решение

Разделить данные и execution path на две ветки:

```text
Текстовые факты
→ RAG по годовым отчетам

Точные финансовые значения
→ структурированное хранилище FinancialFact
```

`FinancialFact` хранит:

- `company_id`;
- `period`;
- `standard`;
- `metric`;
- `value`;
- `unit`;
- `doc_id`;
- `page`;
- `extraction_method`;
- `confidence`.

Годовые отчеты используются как основной корпус для текстового RAG.

Консолидированная отчетность по МСФО используется как источник точных
финансовых фактов.

### Последствия

Преимущества:

- точные числа не зависят от качества semantic retrieval;
- каждый финансовый факт сохраняет provenance;
- можно детерминированно нормализовать единицы;
- можно безопасно строить сравнения и расчеты;
- проще диагностировать ошибки отдельно в RAG и в structured data layer.

Ограничения:

- требуется отдельный pipeline извлечения финансовых фактов;
- для новых форматов отчетности могут понадобиться новые layout-конфигурации;
- отсутствующие disclosures не должны автоматически восстанавливаться LLM.

## ADR-005: Детерминированные финансовые расчеты вместо вычислений LLM

### Контекст

Часть пользовательских запросов требует не поиска готового значения,
а вычисления на основе нескольких финансовых фактов.

Примеры:

- `Net Debt / EBITDA`;
- рассчитанный Free Cash Flow;
- изменение показателя между периодами;
- процентный рост или снижение;
- приведение показателей к одной единице измерения перед сравнением.

LLM способен выполнять арифметику, но такой подход:

- не гарантирует точность;
- плохо воспроизводится;
- затрудняет тестирование;
- затрудняет отслеживание исходных фактов;
- может привести к арифметически правдоподобной, но неверной цифре.

### Решение

Все детерминированные финансовые операции выполнять в Python.

Основной принцип:

```text
LLM
→ понимает пользовательский вопрос

Structured data
→ предоставляет исходные финансовые факты

Python
→ выполняет нормализацию и расчеты
```

Для денежных значений используется `Decimal`.

LLM не выполняет самостоятельно:

- unit normalization;
- Net Debt / EBITDA;
- Free Cash Flow;
- absolute change;
- growth percentage;
- numeric comparison.

Результат расчета должен сохранять исходные `source_facts`,
чтобы ответ можно было связать с конкретными документами и страницами.

### Последствия

Преимущества:

- воспроизводимые расчеты;
- точные unit conversions;
- возможность unit-тестирования;
- прозрачный provenance;
- снижение риска арифметических hallucinations.

Ограничения:

- каждая новая производная метрика требует явной реализации;
- необходимо отдельно определять экономический смысл формулы,
  а не только математическое выражение.

## ADR-006: Parser → Validator → Resolver → Dispatcher как orchestration layer

### Контекст

Пользователь формулирует запросы на естественном языке.

Один и тот же смысл может быть выражен по-разному:

- «Какая выручка Роснефти за 2025 год?»
- «Сколько Роснефть получила выручки в 2025?»
- «Как изменилась выручка Роснефти год к году?»
- «Какие риски описывает ЛУКОЙЛ?»

Если позволить LLM одновременно:

- понимать вопрос;
- выбирать инструмент;
- восстанавливать отсутствующие параметры;
- выполнять расчеты;
- формировать финальный ответ,

то логика становится трудно контролируемой и трудно тестируемой.

### Решение

Разделить orchestration на независимые этапы:

```text
Question
   ↓
Parser
   ↓
Validator
   ↓
Resolver
   ↓
Dispatcher
   ↓
Tool
   ↓
Answer Formatter
```

#### Parser

LLM используется только для преобразования natural-language вопроса
в `ParsedQuestion`.

Поддерживаемые intents:

- `qualitative`;
- `fact`;
- `derived_metric`;
- `comparison`;
- `growth`;
- `unknown`.

Parser не выполняет финансовые расчеты и не должен придумывать
отсутствующие параметры.

#### Validator

Проверяет:

- поддерживается ли компания;
- поддерживается ли метрика;
- хватает ли обязательных параметров;
- соответствует ли структура запроса выбранному intent.

#### Resolver

Используется только там, где параметр можно восстановить безопасно
из доступных данных.

Например, для growth-запроса без указанных периодов resolver может выбрать
периоды только при наличии достаточных фактов и допустимой temporal comparability.

#### Dispatcher

Выбирает детерминированный tool:

```text
qualitative
→ retrieve_docs

fact
→ query_facts

derived_metric
→ compute_metric

comparison
→ compare_companies

growth
→ calculate_growth
```

`unknown` не перенаправляется принудительно в ближайший инструмент.

### Последствия

Преимущества:

- каждый слой можно тестировать отдельно;
- проще диагностировать ошибку;
- LLM не получает лишнюю ответственность;
- unsupported requests не маскируются под поддерживаемые;
- business logic остается в обычном Python-коде.

Ограничения:

- архитектура сложнее простого «один prompt → один answer»;
- необходимо поддерживать контракт между несколькими слоями.

## ADR-007: Semantic и temporal comparability как финансовые guardrails

### Контекст

Математически сравнить два числа недостаточно.

Одинаково названный финансовый показатель может иметь:

- разный экономический scope у разных компаний;
- разные правила представления;
- изменение методологии между отчетными периодами;
- restatement или reclassification.

Поэтому вычисление может быть математически корректным,
но экономически вводить пользователя в заблуждение.

В проекте возникли два разных типа проблемы:

1. сравнение одной метрики между компаниями;
2. сравнение одной метрики одной компании между периодами.

### Решение

Разделить comparability на два уровня.

#### Semantic comparability

Используется при сравнении компаний.

Результат сравнения должен возвращать не только числа,
но и статус методологической сопоставимости.

Например:

```text
COMPARABLE
CAUTION
```

Если определения показателя различаются по scope,
система должна явно показать оговорку.

#### Temporal comparability

Используется для динамики между периодами.

Поддерживаются статусы:

```text
COMPARABLE
NOT_COMPARABLE
UNKNOWN
```

Смысл статусов:

- `COMPARABLE` — сравнение разрешено;
- `NOT_COMPARABLE` — известно, что сравнение некорректно;
- `UNKNOWN` — сопоставимость не подтверждена.

Если метрика имеет статус `NOT_COMPARABLE`,
growth calculation блокируется.

Если данных недостаточно для подтверждения сопоставимости,
система не должна автоматически считать периоды сопоставимыми.

### Последствия

Преимущества:

- предотвращаются экономически некорректные сравнения;
- система различает отсутствие знания и известную несопоставимость;
- финансовые guardrails находятся в deterministic layer, а не в prompt;
- comparability можно тестировать отдельно.

Ограничения:

- правила сопоставимости требуют ручного анализа отчетности;
- для новых компаний и новых метрик необходима дополнительная методологическая проверка;
- статус `UNKNOWN` может блокировать часть запросов, но это предпочтительнее
  необоснованного расчета.
