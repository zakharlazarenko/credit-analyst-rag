# Архитектурные решения

В этом документе зафиксированы основные архитектурные решения проекта: что именно сравнивалось, почему был выбран текущий подход и какие ограничения у него остаются.

## ADR-001: Выбор PDF-парсера для годовых отчетов

### Контекст

RAG-корпус состоит из годовых отчетов компаний. В них есть как обычный текст, так и сложные таблицы, поэтому было важно выбрать парсер, который достаточно хорошо работает с обоими типами содержимого.

На одинаковых страницах годового отчета ЛУКОЙЛа за 2024 год были протестированы три библиотеки:

- `pypdf`;
- `pdfplumber`;
- `PyMuPDF`.

Для сравнения использовались:

- страница 28 — обычный связный текст;
- страница 30 — таблица климатических рисков.

### Наблюдения

**pypdf**

- В целом корректно извлекал обычный текст.
- Иногда добавлял лишние пробелы внутри слов.
- Содержимое таблиц извлекалось как обычный текст.
- Структура строк и столбцов таблицы не сохранялась.

**pdfplumber**

- Чище извлекал обычный текст.
- Лучше сохранял порядок чтения на сложных страницах.
- `extract_table()` позволял восстановить строки, столбцы и связь между ячейками таблицы.

**PyMuPDF**

- В целом корректно извлекал обычный текст.
- На сложных табличных страницах сильнее дробил текст на отдельные строки.
- Обычный `get_text("text")` не сохранял явную структуру таблицы.

### Решение

В качестве основного PDF-парсера использовать `pdfplumber`.

Для работы с документами использовать:

- `extract_text()` — для извлечения обычного текста;
- `extract_table()` — когда важно сохранить структуру таблицы.

`pypdf` оставить для простых технических операций, например для подсчета количества страниц.

В ходе проекта `pdfplumber` был использован на отчетах всех трех компаний, поэтому это решение закреплено как основное для текущей версии системы.

### Последствия

Преимущества:

- достаточно чистое извлечение текста;
- лучшее сохранение порядка чтения;
- возможность извлекать таблицы как строки и столбцы;
- одна библиотека подходит и для текста, и для части табличных страниц.

Ограничения:

- таблицы, которые продолжаются на нескольких страницах, требуют дополнительной обработки;
- качество парсинга зависит от структуры конкретного PDF;
- для сканированных страниц или страниц, состоящих из изображений, может потребоваться OCR.

## ADR-002: Выбор базового способа поиска и результаты гибридного подхода

### Контекст

Для текстового RAG сравнивались три способа поиска релевантных фрагментов:

1. Dense retrieval на `multilingual-e5-small` — семантический поиск по векторам.
2. BM25 — лексический поиск по совпадению слов и терминов.
3. Гибридный поиск Dense + BM25 через Reciprocal Rank Fusion (RRF).

Сначала оценка проводилась на одном эталонном наборе из 10 вопросов. Для всех вариантов использовались одинаковые условия:

- размер чанка — 1200 символов;
- перекрытие чанков — 200 символов;
- предварительная фильтрация по компании и году;
- `top_k = 5`;
- метрики Recall@1, Recall@3, Recall@5 и MRR.

### Результаты

| Метод поиска | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---:|---:|---:|---:|
| Dense | 0.650 | 0.950 | 1.000 | 0.850 |
| BM25 | 0.550 | 0.600 | 0.600 | 0.650 |
| Hybrid RRF 1:1 | 0.600 | 0.700 | 0.800 | 0.750 |
| Hybrid RRF 2:1 | 0.600 | 0.800 | 0.900 | 0.770 |

### Наблюдения

Dense retrieval показал лучший общий результат.

BM25 иногда поднимал релевантный фрагмент выше, если в вопросе и документе встречались одинаковые термины. При этом на семантических запросах и перефразировках он работал заметно хуже.

Обычный RRF дает Dense и BM25 одинаковый вес. Из-за этого нерелевантный фрагмент, который оба метода поставили достаточно высоко, может обогнать действительно релевантный фрагмент, найденный в основном Dense-поиском.

Weighted RRF с весами 2:1 улучшил гибридный вариант, но все равно не превзошел чистый Dense retrieval.

### Решение

Основным способом поиска оставить Dense retrieval.

BM25 и гибридный поиск сохранить в проекте как экспериментальные варианты, чтобы результаты можно было воспроизвести и сравнить.

Следующим шагом после этого эксперимента стало переранжирование кандидатов с помощью Cross-Encoder.

### Ограничения

Первое сравнение проводилось всего на 10 вопросах. Поэтому дополнительно подбирать веса RRF на этом наборе было бы рискованно: можно было бы просто подстроиться под маленькую выборку.

## ADR-003: Dense retrieval + Cross-Encoder reranking

### Контекст

После выбора Dense retrieval как базового поиска был проведен отдельный эксперимент с переранжированием найденных кандидатов.

Сравнивались три варианта:

1. Dense E5 → Top-5.
2. Dense E5 → Top-20 → GTE reranker → Top-5.
3. Dense E5 → Top-5 → GTE reranker → те же Top-5 в новом порядке.

### Результаты на 20 эталонных вопросах

| Конвейер | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---:|---:|---:|---:|
| Dense | 0.717 | 0.958 | 1.000 | 0.900 |
| Dense Top-20 + GTE | 0.742 | 0.950 | 0.975 | 0.917 |
| Dense Top-5 + GTE | 0.792 | 0.958 | 1.000 | 0.950 |

### Решение

Основной конвейер поиска выглядит так:

```text
предварительная фильтрация по метаданным
→ multilingual-e5-small Dense Top-5
→ gte-multilingual-reranker-base
→ Top-5 после переранжирования
```

Reranker не расширяет набор кандидатов, а только меняет порядок уже найденных Dense Top-5.

Такой вариант сохраняет Recall@5 = 1.0 и одновременно улучшает Recall@1 и MRR.

### Ограничения

20 эталонных вопросов — все еще небольшая выборка. Полученные метрики показывают преимущество выбранной схемы на текущем наборе, но не означают, что она будет оптимальной для любого нового корпуса.

## ADR-004: Разделение текстового RAG и структурированных финансовых фактов

### Контекст

В проекте есть два принципиально разных типа пользовательских запросов.

Первый тип — качественные вопросы по содержанию документов, например:

- какие риски описывает компания;
- какие стратегические приоритеты указаны в отчете;
- какие факторы влияли на деятельность компании.

Для таких вопросов нужен поиск релевантных фрагментов текста и генерация ответа с опорой на найденный контекст.

Второй тип — запросы точных финансовых значений, например:

- выручка за конкретный год;
- EBITDA;
- чистый долг;
- операционный денежный поток.

Использовать векторный поиск как источник точных чисел ненадежно. Он ищет текст, похожий по смыслу, но не гарантирует, что будет найдено именно нужное значение, за нужный период и в нужной единице измерения.

### Решение

Разделить систему на две ветки:

```text
Текстовые факты
→ RAG по годовым отчетам

Точные финансовые значения
→ структурированное хранилище FinancialFact
```

`FinancialFact` хранит:

- `company_id`;
- `period`;
- `standard`;
- `metric`;
- `value`;
- `unit`;
- `doc_id`;
- `page`;
- `extraction_method`;
- `confidence`.

Годовые отчеты используются как основной корпус для текстового RAG.

Консолидированная отчетность по МСФО используется как источник точных финансовых значений.

### Последствия

Преимущества:

- точные числа не зависят от качества семантического поиска;
- для каждого финансового факта сохраняется источник: документ, страница и способ извлечения;
- единицы измерения можно нормализовать детерминированно;
- расчеты и сравнения можно строить на структурированных данных;
- ошибки в текстовой и числовой ветках проще диагностировать отдельно.

Ограничения:

- нужен отдельный процесс извлечения финансовых фактов;
- для новых форматов отчетности могут понадобиться новые настройки извлечения;
- данные, которых нет в отчетности, система не должна автоматически придумывать или восстанавливать с помощью LLM.

## ADR-005: Детерминированные финансовые расчеты вместо вычислений LLM

### Контекст

Некоторые вопросы требуют не поиска готового значения, а расчета на основе нескольких финансовых фактов.

Например:

- Net Debt / EBITDA;
- рассчитанный Free Cash Flow;
- изменение показателя между периодами;
- темп роста или снижения;
- приведение показателей к одной единице измерения перед сравнением.

LLM может выполнять арифметику, но для финансовых расчетов это ненадежный подход:

- нет гарантии точности;
- результат сложнее воспроизводить;
- вычисления труднее тестировать;
- сложнее проследить, какие исходные данные использовались;
- модель может получить правдоподобный, но неверный результат.

### Решение

Все детерминированные финансовые операции выполнять обычным Python-кодом.

Основной принцип:

```text
LLM
→ понимает, что хочет пользователь

Структурированные данные
→ предоставляют исходные финансовые факты

Python
→ нормализует единицы и выполняет расчеты
```

Для денежных значений используется `Decimal`.

LLM не выполняет самостоятельно:

- нормализацию единиц измерения;
- расчет Net Debt / EBITDA;
- расчет Free Cash Flow;
- расчет абсолютного изменения;
- расчет темпа роста;
- арифметическое сравнение значений.

Результат расчета сохраняет исходные `source_facts`, чтобы его можно было связать с конкретными документами и страницами.

### Последствия

Преимущества:

- расчеты воспроизводимы;
- преобразование единиц выполняется однозначно;
- финансовую логику можно покрыть unit-тестами;
- сохраняется прослеживаемость исходных данных;
- снижается риск арифметических ошибок со стороны LLM.

Ограничения:

- каждую новую производную метрику нужно реализовывать явно;
- при добавлении новой формулы необходимо отдельно проверять ее экономический смысл, а не только математическую корректность.

## ADR-006: Разделение обработки запроса на Parser → Validator → Resolver → Dispatcher

### Контекст

Пользователь задает вопросы на естественном языке, и один и тот же смысл можно выразить по-разному:

- «Какая выручка Роснефти за 2025 год?»
- «Сколько Роснефть получила выручки в 2025 году?»
- «Как изменилась выручка Роснефти год к году?»
- «Какие риски описывает ЛУКОЙЛ?»

Если позволить LLM одновременно понимать вопрос, выбирать инструмент, восстанавливать недостающие параметры, считать показатели и формировать финальный ответ, система становится сложнее для контроля и тестирования.

### Решение

Разделить обработку запроса на несколько независимых этапов:

```text
Вопрос
  ↓
Parser
  ↓
Validator
  ↓
Resolver
  ↓
Dispatcher
  ↓
Инструмент
  ↓
Answer Formatter
```

#### Parser

LLM преобразует вопрос на естественном языке в структурированный `ParsedQuestion`.

Поддерживаются следующие типы запросов:

- `qualitative` — качественный вопрос по содержанию документа;
- `fact` — запрос точного финансового значения;
- `derived_metric` — расчет производного показателя;
- `comparison` — сравнение компаний;
- `growth` — анализ изменения показателя между периодами;
- `unknown` — неподдерживаемый или нераспознанный запрос.

Parser не выполняет расчеты и не должен придумывать отсутствующие параметры.

#### Validator

Проверяет:

- поддерживается ли компания;
- поддерживается ли метрика;
- хватает ли обязательных параметров;
- соответствует ли структура запроса выбранному типу.

#### Resolver

Восстанавливает недостающие параметры только тогда, когда это можно сделать однозначно и безопасно на основе доступных данных.

Например, если в вопросе о динамике показателя не указаны периоды, Resolver может выбрать их только при наличии подходящих фактов и подтвержденной сопоставимости.

#### Dispatcher

Выбирает, какой инструмент должен обработать запрос:

```text
qualitative
→ поиск по документам через RAG

fact
→ запрос к FinancialFact Store

derived_metric
→ расчет производной метрики

comparison
→ сравнение компаний

growth
→ расчет изменения показателя
```

Запрос с типом `unknown` не перенаправляется автоматически в «ближайший» инструмент.

### Последствия

Преимущества:

- каждый слой можно тестировать отдельно;
- легче понять, на каком этапе возникла ошибка;
- LLM отвечает только за те задачи, где действительно нужно понимание языка;
- неподдерживаемые запросы не маскируются под поддерживаемые;
- основная бизнес-логика остается в обычном Python-коде.

Ограничения:

- архитектура сложнее, чем схема «один запрос → один промпт → один ответ»;
- нужно поддерживать согласованные контракты между слоями.

## ADR-007: Проверка сопоставимости финансовых показателей

### Контекст

Для финансового анализа недостаточно просто математически сравнить два числа.

Показатель с одинаковым названием может:

- иметь разный экономический охват у разных компаний;
- рассчитываться по разным правилам;
- менять методологию между отчетными периодами;
- быть пересмотрен или переклассифицирован в новой отчетности.

Поэтому расчет может быть математически правильным, но экономически некорректным.

В проекте рассматриваются два вида сопоставимости:

1. сопоставимость показателя между разными компаниями;
2. сопоставимость одного и того же показателя одной компании между периодами.

### Решение

Разделить проверку сопоставимости на два уровня.

#### Семантическая сопоставимость

Используется при сравнении компаний.

Система возвращает не только числовые значения, но и статус методологической сопоставимости.

Например:

```text
COMPARABLE
CAUTION
```

Если одинаково названные показатели имеют разный экономический охват, система должна явно предупредить об этом.

#### Временная сопоставимость

Используется при сравнении разных периодов одной компании.

Поддерживаются статусы:

```text
COMPARABLE
NOT_COMPARABLE
UNKNOWN
```

Их смысл:

- `COMPARABLE` — сравнение допустимо;
- `NOT_COMPARABLE` — известно, что сравнение некорректно;
- `UNKNOWN` — сопоставимость не удалось подтвердить.

Если показатель имеет статус `NOT_COMPARABLE`, расчет динамики блокируется.

Если данных недостаточно, система не должна автоматически считать периоды сопоставимыми.

### Последствия

Преимущества:

- снижается риск экономически некорректных сравнений;
- система различает «сопоставимость не подтверждена» и «сопоставимость точно отсутствует»;
- правила проверки находятся в детерминированном коде, а не только в промпте;
- логику сопоставимости можно тестировать отдельно.

Ограничения:

- правила сопоставимости требуют ручного анализа отчетности;
- при добавлении новых компаний и метрик нужна дополнительная методологическая проверка;
- статус `UNKNOWN` может блокировать часть расчетов, но это безопаснее, чем выдавать необоснованный результат.
